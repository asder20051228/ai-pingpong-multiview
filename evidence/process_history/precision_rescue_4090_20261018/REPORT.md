# 4090 丢点排查与独立方案复测

## 结论

已恢复全部 86 个命中：**TP 86 / FP 1 / FN 6，准确率分 71.3854/75**。新方案保留冻结 4090 版全部 84 个命中，找回与 4070 最好版本相同的两个 GT；匹配到的 86 个 GT 身份完全一致。三轮新方案输出 SHA256 完全相同。

本次未改冻结模型、原规则文件、原预测、数据、官方 core/run.py/validate.py。新方案位于独立实验目录，未覆盖生产版。所有正式复测都是原始 run.py、同一 15 段公开验证视频、2109 帧、同一冻结评分器；不是平台隐藏测试成绩，也不构成未参与调参数据上的泛化验证。

## 一个必须纠正的环境结论

此前 4090 测速用了 `--decoder gpu`，但这台服务器的视频硬解码没有成功。FFmpeg 报告 `cuvidGetDecoderCaps ... CUDA_ERROR_NO_DEVICE` 后回退到 CPU；官方解码模块在 FFmpeg 退出码为 0 时没有展示 stderr。

驱动直连实验：两台机器 cuInit/cuCtxCreate 均成功；4070 的 cuvidGetDecoderCaps=0、supported=1；4090 返回 100、supported=0。因此 CUDA 计算可用、NVDEC 当前不可用。该故障独立于 TensorRT 和 FFmpeg。尚未修复宿主机/容器的 NVDEC 可用性，没有重装驱动或重启机器。

所以本文及此前 4090 速度都应理解为**GPU 推理 + 实际 CPU 回退解码**，不能标为已验证的 GPU 硬解码速度。下一步应由租用平台检查该实例的视频解码设备/驱动暴露，再做真实 GPU 解码下的速度和准确率复测。

## 两个丢失命中的证据

| 目标 | 4070 原 GPU 路径 | 4090 回退路径 | 单变量反事实 |
|---|---|---|---|
| v000001，GT 第45帧 | 第44帧置信度 0.802246 | 0.799316，跨过 0.80 参考帧阈值 | 只恢复置信度即可找回第45帧；只恢复坐标无效 |
| v000066，GT 第2帧 | 第3帧相邻纵向差 0.9053 px | 0.3870 px，低于 0.5 px | 只恢复坐标即可找回第3帧预测（容差内匹配 GT2）；只恢复置信度无效 |

第二处具体是热图像素 (277,154) 从 0.703125 变为 0.697266，跨过 0.70 掩码阈值，质心采用的像素从 16 个减至 15 个，球心 y 发生约 0.515 px 偏移。没有缺帧：相关三段视频共446帧，帧数和顺序均一致。

### 分离 TensorRT 与解码影响

1. 4090 FFmpeg CPU/GPU 选择的 446 帧 RGB 和模型输入逐字节一致（原因是 GPU 路径回退）。4090 官方 CPU 全量入口输出也与原 GPU 选择输出逐字节相同：84/2/8。
2. 4070 官方 CPU 全量入口同样变为84/2/8。其 RGB 与4090回退路径逐帧相同；相同输入下两台原生 FP16 引擎仍有小数值差别，但两处都丢失，掩码变化也相同。
3. 三处目标帧的原始 YUV 内容跨两台机器一致；4070 真正 GPU 解码的 RGB 输出与 NV12 转换路径一致，CPU 回退时的转换结果不同。4090 显式经 NV12 转 RGB 后，三段视频全部446帧RGB均与4070 GPU路径逐字节一致。
4. **只在诊断脚本里统一 NV12 转换，保留4090原生FP16引擎和全部冻结规则，就找回两处命中，并消除 v000085 第178帧新增误检。** 这是解码/颜色转换路径引发差异的直接证据。此脚本是诊断，不冒充正式入口成绩。
5. 4090 正式入口只改球模型为严格 FP32（FP16、TF32均关闭），仍84个命中，只把误检从2降至1。两处漏检的主要来源是输入转换差异引发的阈值跨越；TensorRT 的数值误差另外影响第178帧边界误检。

## 独立方案与对照

所有正式入口的 GPU 解码选择仍处于上述回退状态。球台模型保持原 FP16。

| 对照 | TP/FP/FN | 准确率分 /75 |
|---|---|---:|
| 冻结4090版 | 84/2/8 | 70.0136 |
| 4090 原版，官方 CPU 解码 | 84/2/8 | 70.0136 |
| 4090 原版，球模型严格 FP32 | 84/1/8 | 70.3379 |
| 仅置信度边界补救 | 85/2/7 | 70.7188 |
| 仅浅反弹边界补救 | 85/2/7 | 70.3557 |
| 两项补救，保持 FP16 | 86/2/6 | 71.0609 |
| 两项补救，全程严格 FP32 | 86/1/6 | 71.3854 |
| 仅按需 FP32 复核 | 84/1/8 | 70.3379 |
| 两项补救 + 按需 FP32 复核 | 86/1/6 | 71.3854 |

新方案使用统一规则，没有视频编号、特定帧号或GT坐标条件：

- 基础输出保留；额外候选仅来自连续轨迹、已接纳的多通道补观测附近，并要求真实顶点置信度≥0.8、强向上速度变化、水平运动一致性、球台范围和颜色支持，通过原有时间/空间去重。
- 补救分支允许参考置信度0.795–0.800的边界，以及0–0.5像素的浅反弹；两项分别只恢复一处，组合恢复两处。
- 球模型 FP16 的中间通道最高置信度距离0.800不超过0.005时，用关闭TF32的FP32复核该热图；本次每轮 **14 / 2109 帧**触发。其余帧继续FP16。
- `adaptive_solution:Solution` 是本次推荐的独立实验入口。`rescue_solution:Solution` 为纯FP16补救对照，`rescue_solution:StrictSolution` 为全程FP32对照。

FPS口径为官方 run_status 的 total_frames / infer_sec，含解码、预处理、推理、轨迹和后处理。新方案准备时间分别为 [1.9, 1.9, 1.9] 秒，另列、不包含在FPS中。首次严格FP32球引擎构建71.7秒；此缓存保留。没有达到50 FPS满分线；实测最低值不是其他服务器上的速度保证。

## 双卡4090是否有用

赛题第152行写的是“Intel CPU + 2×4090，最多使用两张”，不是要求必须同时使用两张。当前实例实际只有一张4090、16核CPU时间配额。

当前官方Runner按视频串行执行，两个TensorRT模型默认使用cuda:0，每次推理同步；现方案未实现双卡并行。因此仅换到双卡机器，不会自动把上述FPS翻倍，也不能据此保证达到50 FPS。第二张卡需要方案显式安排并行计算才可能获益，且还受CPU解码、预处理及串行接口限制。双卡实际收益需在真正的两卡环境中测量；本次未实测双卡。
